# 0024 – Phase-one media format and privileged PBS launcher API

- Status: implemented; disposable loop/KVM acceptance passed
- Date: 2026-11-11
- Implements: phase one of [0023](0023-backup-stick.md)

## Decision

1. Keep the existing rescue ISO boot behavior and add the official
   `proxmox-backup-server` package from `pbs-no-subscription`, verified with the
   same pinned Proxmox archive key. Mask PBS services/timers, SSH aliases/socket
   and mail services during image construction. Direct namespace launch bypasses
   those units deliberately; no PBS starts on the live system's network.
2. The media writer reuses `rescue::guard::assess` and
   `rescue::exec::check_disk_free`. Confirmation always requires the disk name;
   nonempty targets additionally require the exact `ERASE <name>` phrase.
   A hidden image-file test mode allocates its own loop; arbitrary pre-existing
   loops are not offered as ordinary targets. All writer mounts are private.
3. The GPT has a 1 MiB BIOS boot partition, a FAT32 ESP sized for two complete
   release payloads plus overhead, and the remaining ext4 data partition (at
   least 2 GiB), made with `mkfs.ext4 -m 0`. `/live/a` and `/live/b` are the slots;
   `nestegg/` is the root-owned mount anchor; PBS owns its `store/` child.
   Boot and data UUIDs are recorded in a versioned marker and cross-checked against the actual devices.
4. Avoid replacing a single active selector on FAT during update. The top-level
   GRUB dispatcher stays fixed. Each slot has a generation, boot configuration
   and checksum commit. Copy and compare the complete inactive payload,
   fsync every payload file and directory, write and fsync its boot configuration,
   then publish and fsync its checksum and parent directories last. GRUB
   validates both configurations and chooses the newest committed
   generation, with the other committed slot as a manual fallback entry. Payload
   checksums also reject truncated live files. Both slots still share FAT metadata;
   a torn FAT sector can damage either slot (see 0025).
   BIOS and UEFI both pin GRUB and live-boot to this ESP's filesystem UUID.
5. Create/update/add install the desktop squashfs only from a private copy of a
   root-owned release ISO on fixed storage, checked against an independent
   `--sha256` pin or a similarly protected adjacent checksum. This is integrity
   checking, not cryptographic authentication of a release. The mutable medium
   never supplies desktop code. Root-owned, non-writable path components protect the
   desktop cache; a root-owned sticky ancestor permits isolated scratch tests.
   The local launcher uses only `/var/lib/nestegg/stick/pbs.squashfs`, verifies its
   recorded checksum and refuses FAT/removable backing storage. No free image
   path remains in `LauncherOptions`.
6. `stick add` preserves the configuration document and records distinct ext4
   UUIDs under `[stick].data_uuids`. Existing `[pbs]` configurations remain valid;
   unknown fields remain errors. Phase one accepted registration-only documents
   without enabling backups. Phase two ([0026](0026-desktop-stick-target.md))
   extends this with stick-only targets and full-system defaults on first
   registration, preserving existing explicit backup settings. Registration and
   settings share a lock and the owner/mode-preserving atomic writer; a new
   configuration is root:nestegg 0640.
7. Expose `stick::launcher::{LauncherOptions, LocalPbs, preflight}`. Startup runs
   the trusted embedded helper as root, with mount/PID/network/UTS namespaces,
   private devices, RAM overlay, fresh configuration and real tmpfs `/run`.
   Supply localhost/hostname files normally generated by live-config when the
   ISO boots, and resolve `backup` ownership inside the image. Lock the mounted
   datastore
   against concurrent local handles, pin its root-owned anchor by directory fd,
   preserve PBS-created permissions in `store/`, use `nestegg@pbs!stick` on every launch and regenerate the token/certificate.
   Return a network-namespace descriptor and a memory-backed token descriptor.
   `client_command` supplies only `nsenter --net`, keeps source mounts visible,
   and inherits the token as fd 9. A stable supervisor thread owns the helper
   process, so Linux parent-death signals cannot tie its lifetime to a
   short-lived thread that called `start`. The handle must outlive its clients; `stop`
   kills and reaps the helper, waits for namespace PID 1 to exit, and dropping
   it performs the same cleanup. Startup waits for all API authentication keys
   and the API socket before starting the proxy.
8. Check AF_INET6 socket creation before privileged startup. A kernel without it
   is unsupported; never change host sysctls, boot options or firewall rules.
   Rootless operation remains unsupported, as demonstrated in phase zero.

## Verification boundaries

Acceptance uses disposable sparse files, owned loops, SeaBIOS and OVMF. It tests
an interrupted write, not a physical flash-controller power failure. The data
partition and existing encrypted snapshots must survive updates. New desktop
backup scheduling, hotplug services, target state and key copies are covered
by phase two (0026); local-datastore wizard flows remain later phases.
Decision 0023 remains proposed until the complete feature and its hardware gate
pass. A release README claim is not
added merely because media preparation exists.

## Original phase-one acceptance result (2026-11-11, before 0025 hardening)

The real CLI created/registered an 8 GiB disposable sparse image. The launcher
completed encrypted backup/restore, restart with fresh certificate/token,
owner-preserving datastore reuse, rejection of concurrent local servers, host
mount-namespace preservation and unchanged host listeners. Eight KVM boots
passed: SeaBIOS and OVMF before update, after update, after a controlled SIGTERM
halfway through copying the inactive squashfs, and after retry. A competing
rescue ISO was attached; the live system still mounted the correct GPT medium
and slot. PBS, SSH and mail masks were checked in the booted guests. Partition
layout and hashes of all existing datastore files survived unchanged. After those preservation checks, a deliberate recreation of the owned image
exercises the second ERASE confirmation and replacement of an existing ext4
filesystem. All owned loops, mounts and processes were cleaned up. No physical USB medium was used.
