# 0034 – A hub: one place to manage all computers, one command to add one

- Status: accepted, not implemented (stages below)
- Date: 2026-11-14
- Supersedes: 0003 row "Multi-machine overview … No central service"
- Extends: 0018 (key export must be proven), 0013 and 0022 (settings a group
  member may change)

## Context

The maintainer set nestegg up by hand on a fresh machine, as a user would.
Result: far too many steps. Per computer, in the PBS web interface: create an
API token, give user and token a role on the namespace, copy the certificate
fingerprint. Then on the computer: install the client from a third-party
repository, install the package, `init` with five options, store the secret,
create a key, export it, prove the export, enable three units, join a group,
log in again. The web interface only helps after most of this is done, and it
is reachable only on the computer itself. Managing three computers means
doing all of it three times and opening three separate interfaces.

What is wanted instead: **one instance in the home network that manages the
backups of all computers, and adding a computer is one command.**

0003 ruled out a central service ("nothing extra to host, secure, or
update"). That reasoning holds for a single computer, and standalone use
stays possible. For a household it put the whole burden on the person,
repeated per machine.

## Decision

nestegg gets an optional central component, the **hub**.

1. **Same binary, same package.** `nestegg hub init` and
   `nestegg-hub.service` turn any always-on Linux machine (a small container
   is enough) into the hub. It must not be a machine that sleeps; a PBS that
   is woken by Wake-on-LAN is therefore the wrong host.

2. **The hub is never in the data path.** Computers back up directly to the
   PBS with the official client, exactly as today. If the hub is off or gone,
   backups, restores and the rescue stick keep working. The hub provisions,
   shows and controls; it never sees backup data and holds no encryption key.

3. **One PBS user instead of manual tokens.** The hub is given one PBS user
   that has `DatastoreBackup` on the household namespace, and nothing else.
   For every computer that joins, the hub logs in as that user and creates an
   API token (`<user>!<computer>`) plus its ACL entry. PBS allows a user
   without further privileges to do exactly this for its own tokens, and a
   token can never exceed its user (verified against PBS 4.2: token creation,
   ACL for the own token, deletion; ACL entries for other users are refused).
   Each computer still has its own secret, backups are still owned per
   computer, and nobody in this chain can delete backups.
   `hub init` can do the PBS preparation as well (namespace, user, role) when
   an administrator login is given once; it is used for these calls and not
   stored.

4. **Adding a computer is one command.** In the hub, "Add computer" shows a
   command line containing the hub address, the pin of its certificate and a
   one-time code (valid 30 minutes, one use):

   ```sh
   curl -fsSk --pinnedpubkey 'sha256//<PIN>' https://hub.example.com:8443/join.sh \
     | sudo sh -s -- <CODE>
   ```

   The script installs the backup client (Proxmox repository with the pinned
   key checksum) and the nestegg package (served by the hub with its
   checksum), then runs `nestegg join`. `join` receives server, datastore,
   namespace, PBS fingerprint, Wake-on-LAN address, its new token and the
   household defaults; writes the configuration; stores the secret; creates
   the encryption key; enables the units; adds the calling user to the group
   `nestegg`; and starts the first backup. No option has to be typed.
   `sudo nestegg join <url> --pin <PIN> --code <CODE>` does the same for an
   already installed package.

5. **One household master key instead of one key copy per computer.**
   `hub init` creates an RSA master key pair with the official client
   (`key create-master-key`), hands the private part to the administrator as
   a paper key or file, and requires the proof of 0018 once (check code or
   the file itself). After the proof the private part is deleted from the
   hub; only the public key stays and is given to every computer. Each
   computer creates its own key as before and backs up with
   `--master-pubkey-file`, so a copy of its key, encrypted to the master
   key, lies in every snapshot (verified with client 4.2.8: the key
   recovered with `key import-with-master-key` has the same fingerprint).
   For such a computer the gate "backups only after the key copy is proven"
   is met by the proven master key; its own paper key stays possible.
   Consequences that are accepted: whoever holds the master key can read the
   backups of every computer of the household; whoever loses it and a
   computer loses that computer's backups. The hub cannot read anything.

6. **The hub's web interface is reachable in the network, with a login.**
   HTTPS with a certificate created at `init` (an own certificate can be
   configured), an administrator password, session cookies. It lists all
   computers with the state of their backups and opens each computer with
   the same screens the local interface has.

7. **Control goes through a connection the computer opens.** A joined
   computer's daemon keeps an outgoing, pinned HTTPS connection to the hub
   and authenticates with a credential from `join`. The hub forwards API
   requests for that computer over it (same contract, `api/openapi.yaml`).
   Nothing new listens on the computers, and computers behind a firewall or
   asleep need no special handling: an absent computer is shown with what
   the PBS knows (last snapshot and its status report), and actions are
   unavailable, not queued.
   Requests from the hub act as a member of the group `nestegg`, never as
   root: status, history, starting a backup, the settings of 0013 with the
   reporting of 0022. Restores started from the hub write files as some
   user of that computer and need their own decision (stage 3).

8. **The local interface stays** (`nestegg ui`, loopback only, 0003). A
   computer can leave the hub (`nestegg leave`) and keeps backing up.

## What a compromised hub can do

It holds the PBS user's password: read the encrypted backups, add
snapshots, create tokens; not delete, not decrypt. It can start backups
and change the 0013 settings on joined computers (changes that reduce
protection are reported there, 0022). It serves the package and the script
that a **new** computer runs as root, so it can take over computers that
join after the compromise. The hub is therefore a machine to protect like
the PBS itself; the documentation says so. Once public releases exist, `join`
checks the package against the release checksum instead of trusting the hub.

## Stages

1. **Join and overview.** `hub init` (PBS user, certificate, password,
   master key with proof), PBS preparation, one-time codes, `join.sh`,
   `nestegg join`/`leave`, package serving, backups with the master public
   key, `nestegg key recover` (key of a computer from a snapshot and the
   master key), hub interface with login and the list of computers from the
   PBS. End-to-end test: hub, PBS and two computers in containers.
2. **Control.** The outgoing connection, forwarding of the API, the full
   per-computer screens in the hub, the rescue stick accepts the master key.
3. **Later, each with its own decision.** Restores from the hub, backup
   sticks in the hub, updating the package on the computers.

Publication (0001, the planned move to a new repository) waits until
stages 1 and 2 are done.

## Not decided here

- Several households or several administrators on one hub.
- A hub outside the home network.
